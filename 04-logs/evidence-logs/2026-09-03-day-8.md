# Day 8 — Thursday 3 September — Authentication and Authorisation

## Built
Sanctum token authentication with register/login/logout endpoints, role-based access control via Policies (employee vs approver), rate limiting on login (5 attempts/minute), consistent 401/403/429 error responses.

## Architecture
- **AuthController:** register (creates user + token), login (validates credentials + creates token), logout (revokes token)
- **OrderPolicy:** enforces row-level access (employees see own records, approvers see all)
- **OrderController:** every endpoint calls `$this->authorize()` to check Policy before returning data
- **Rate limiting:** throttle:5,1 middleware on POST /login
- **Error envelope:** consistent JSON shape across 401/403/422/429 responses

## Test Coverage

4. ✅ Protected routes: 401 without token, 403 without authorization

## Attack scenarios tested
- **Cross-user access:** User B with token_B tries PUT /orders/260 (User A's order) → 403 Forbidden ✓
- **Revoked token:** After logout, old token returns 401 Unauthorized ✓
- **Malformed tokens:** Garbage string, valid format from different app, no token → all return 401 ✓
- **Deleted user with old token:** 401 Unauthorized (Sanctum middleware catches missing user) ✓
- **Multiple logins:** Both tokens remain active (design choice documented) ✓

## Design decisions
- **Multiple login tokens:** Currently keeps both tokens active. Decision: maintain as-is (simpler, user can logout specific session if UI supports it)
- **Role column in users table:** Simple role field, not a full RBAC library (adequate for 2-role system)
- **Policy at row level, not endpoint level:** Every endpoint accessible to authenticated users; Policy controls what data they see (cleaner than URL-level role gates)

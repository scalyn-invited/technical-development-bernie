# Day 12 — Evidence — REST Endpoints, Validation, Structured Responses

Environment: PHP 8.2.12 · Laravel Framework 12.69.1 · Laravel Sanctum 4 · SQLite
Verification method: `php artisan migrate:fresh --seed`, then `php artisan serve --port=8123` driven with `curl`. Real HTTP requests through the full stack as both roles. Automated tests are Day 14; nothing below is an assertion about what the code would do.

Run from a clean database. One administrator, three members at the three plan stages, six active skills and one retired. The administrator is given a development plan of their own (plan 4) so the integrity rule has a subject to be tested against.

---

## 1. The routes under test

```
POST       api/login                                ->  AuthController@login

GET|HEAD   api/skills                               ->  SkillController@index
POST       api/skills                               ->  SkillController@store
PATCH      api/skills/{skill}                       ->  SkillController@update

Showing [12] routes
```

Twelve routes: the four authentication endpoints from Day 11, plus the eight this day was for. The two thin Day 11 authorisation-surface routes are gone — `GET /plans/{plan}` and `POST /plans/{plan}/assessments` are now the real endpoints, with Form Requests and API Resources behind them.

############ 12. THE CONCURRENCY CASE - a unique-constraint race ############
Two requests posting the same week number both pass the unique VALIDATION rule,
because validation is check-then-write. The loser reaches the database constraint.
Simulated by removing only the unique rule, so the request arrives at the database
in exactly the state the losing half of a real race arrives in.

--- BEFORE the fix: the collision with no arm for it in the envelope
  keys returned: message, exception, file, line, trace
  message: SQLSTATE[23000]: Integrity constraint violation: 19 UNIQUE constraint failed: weekly_entries.development_plan_id, weekly...
  exception: Illuminate\Database\UniqueConstraintViolationException
  NOT the envelope - no error/code/details, and the response body carries the SQL,
  the database path and a full stack trace.
<<HTTP 500>>

--- AFTER the fix: the identical collision, envelope arm in place

## 6. Counter-test — what `->scopeBindings()` prevents

Check 53 proves the scoped route returns 404. It does not, on its own, prove that anything was being prevented. Re-run with `->scopeBindings()` removed and nothing else changed:

```
--- state of week 10 (week 4 on plan 2) before the test
    id=10 plan=2 objective="Ship the eight REST endpoints with resources "

--- scopeBindings() removed; the SAME cross-plan request:
  ACCEPTED: week id 10, development_plan_id=2, objective now "Written through plan 1 to a week that belongs to p"
  <<HTTP 200>>

--- scopeBindings() restored; the same request again:
{"error":true,"code":"not_found","message":"Resource not found.","details":[]}
<<HTTP 404>>
```

Unscoped, `PATCH /plans/1/weeks/10` returned 200 and wrote to plan 2's week. The authorisation check ran against plan 1 — the plan named in the path — while the write landed on a row belonging to plan 2. An administrator barred from touching their own plan could have edited it by addressing the request through somebody else's.

This is the integrity rule defeated by a URL, and it is invisible in a passing test suite that only ever addresses rows through their correct parent.

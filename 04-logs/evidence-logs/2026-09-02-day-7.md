# Day 7 — Wednesday 2 September — REST API design: resources, status codes, validation, structured errors

## Built
REST API for Orders entity with OrderResource, OrderResourceCollection, consistent JSON error envelope, and correct HTTP status codes (200/201/204/404) on all endpoints.

## Learned
Eloquent API Resources centralize model serialization; Form Request validation and authorization happen before the controller; Laravel 11's `validateCsrfTokens(except: ['api/*'])` is the way to exempt routes from CSRF; consistent error envelopes must be enforced at every failure path (404, validation, server errors).

## Got wrong
1. Initial CSRF middleware configuration—tried middleware aliases and custom middleware before discovering Laravel 11 requires explicit exception array in bootstrap/app.php
2. FormRequest `authorize()` returning `false` blocks requests at 403 before validation runs—confused this with validation errors
3. Missed the `placed_at` NOT NULL constraint; didn't include it in validation or test payload initially

## AI output rejected
1. Bootstrap/app.php middleware configuration was incomplete; `statefulApi()` didn't solve CSRF issue
2. Initial suggestion to use `withoutMiddleware()` syntax was incorrect for Laravel 11

## Still cannot explain
Why `statefulApi()` exists as a separate method from CSRF exemption—what's the separation of concerns? Also, whether there's a cleaner pattern for handling Laravel 11 middleware configuration than explicit exception arrays.

## Evidence
- OrderController: 5 routes, each with correct status code (show/update/destroy use Order::find not route binding—gap noted in review)
- OrderResource: minimal output (id, customer_id, total, status, created_at)
- StoreOrderRequest: validation for required fields + placed_at
- Test results: GET→200, POST→201, GET 404→404 with consistent error envelope
- Senior review identified: no eager loading visible, no validation error shape tested, placed_at not in output, no authorization checks, no route model binding

## Applied to client work
Not yet — this was foundational Week 2 API design. The error envelope pattern and Resource structure will be the template for the mini-app's authenticated API starting Week 3.

### The five questions, and the one about a decision I had not consciously made

The question that landed was: **"Why does an unauthorised read return 403 rather than 404, and did you decide that or inherit it?"**

I inherited it. It was decided on Day 11 and written into `TECHNICAL-NOTES.md` §7, and I carried it into six new endpoints today without re-examining it once. Re-examined now, the Day 11 reasoning still holds for this tool — hiding the existence of another member's plan is not a threat it defends against, and a 404 there would make a real bug indistinguishable from a permission denial. But "it still holds" is a different statement from "I decided it", and until asked I would have claimed the second.

## The concurrency prompt (the day card's addition to block 45–55)

> Which of my endpoints would behave incorrectly if two requests arrived at the same moment?

Three answers came back. Two were real.

1. **`POST /plans/{plan}/weeks` and `POST /plans/{plan}/assessments`** — both rely on a `unique` validation rule, and both have a window between the `SELECT` and the `INSERT`. Real, and this is the finding that produced the 409 arm. The scenario is not theoretical for this tool: two administrators working the open-weeks queue at the same time is the normal way it will be used.
2. **`POST /skills`** — same shape, on `unique:skills,name`. Real, and covered by the same arm.
3. **`PATCH .../weeks/{week}` closing the same week twice** — claimed as a double-close that would move `closed_at`. **Not real.** The controller keeps the existing timestamp (`$weeklyEntry->closed_at ?? now()`), so a second close is idempotent on the field that matters. Worth noting that this was a decision made while writing the controller for a different reason — that a closed week should not silently change when it was closed — and it happened to answer the concurrency question too.

**Where the answer stops.** 409 makes the loser of a race receive a correct, envelope-shaped error instead of a stack trace. It does not make the operation atomic, and it is not a lock. The one place atomicity is actually required — writing the final score set and completing the plan together, so a partial set never leaves a plan `completed` — is Day 13's transaction, and it is not addressed today.

## AI output that was wrong

1. **The boolean query filter.** Written with a bare `boolean` rule, which made `?active=true` a 422. Laravel's `boolean` accepts `true, false, 1, 0, "1", "0"` and rejects the strings `"true"` and `"false"` — it is a form-post rule applied to a query string. Found by running the endpoint, not by reading the rule; the code looked entirely correct. Corrected by normalising in `prepareForValidation()` rather than loosening the rule, so `?active=maybe` is still a 422. All four spellings and the nonsense value are in the evidence (checks 4–8).
2. **`SkillController::store()` came back with an incoherent ternary** returning a Resource two different ways depending on an `instanceof stdClass` test that meant nothing — and would have returned 200 where the card requires 201. It parsed cleanly, so `php -l` said nothing about it. Rewritten before it ran. This is the second time in two days that generated code was syntactically fine and semantically empty, which is the argument for reading a generated method rather than only running it.
3. **The duplicate-assessment validation message used `:input`**, which interpolates the value of the attribute the rule is attached to. Attached to `skill_id`, it produced *"A 8 score of this type is already recorded"*. Found by reading the response body rather than the rule.

**The pattern across three days.** Day 11's note was that AI-proposed *verification* was twice the thing that was wrong. Today it is different: two of the three failures above were AI-proposed *code* that read correctly and behaved incorrectly, and neither was caught by anything except running it and reading the actual bytes that came back. Both of the day's real design findings, by contrast, came out of Prompt C — which is the review working as intended.

## One framework claim checked against the source rather than accepted

Scoped bindings resolve the parent relationship from the child parameter's name. The working assumption was that `{week}` would find `weeklyEntries()`. Reading `Illuminate\Database\Eloquent\Model::childRouteBindingRelationshipName()` shows it computes `Str::plural(Str::camel($childType))`, so `{week}` would have looked for a `weeks()` relation that does not exist on `DevelopmentPlan`.

Named the parameter `{weekly_entry}` instead, which resolves to `weeklyEntries()`. The URL segment is unaffected — the path is still `/plans/{plan}/weeks/{id}`, because a route parameter's name never appears in the URL.

This was two minutes in `vendor/` against a failure that would have surfaced as a confusing runtime error on an endpoint that appeared to be correctly written.

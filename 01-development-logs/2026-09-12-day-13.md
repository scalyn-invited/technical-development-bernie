## Built

Implemented ProgrammeProgressionService and connected the HTTP endpoints for:
- Draft → active → completed, with no repeat or reverse transitions.
- Nonempty valid baselines at activation; draft-only baseline corrections.
- Plan membership defined by baseline skill IDs, frozen after activation.
- Final scores matching that exact set, saved with completion in one transaction.
- Active-plan weeks with contiguous numbers and prior weeks closed.
- Planned → evidenced → closed, with evidence/outcome validation and closed-week immutability.
- Active, baselined focus skills and deactivation blocked while any open week uses the skill.
- Comparison computed on read as final minus baseline in percentage points using integer hundredths; no stored delta. Deactivated skills remain visible.

New routes: POST plans/{plan}/activate, POST plans/{plan}/complete,
PATCH plans/{plan}/assessments/{assessment}, GET plans/{plan}/comparison
(all under /api and protected by authentication/policies).

## Learning and design decisions

The learner explained the activation prerequisites, immutable baselines, closed weeks, and atomic final-score completion before implementation. Schema inspection established that there is no independent plan-skill assignment list: baseline rows define membership. An omitted intended skill cannot be detected automatically; activation confirms the current nonempty set.

The learner explicitly authorized AI implementation. This was AI-assisted development, not an unaided coding exercise. Evidence/outcome checks now use the locked persisted week plus submitted fields rather than values merged earlier during route binding.

## Learned

**Authorisation has to be decided before validation, and Laravel already does it in that order.** Moving the `Gate` calls out of the controller body and into `FormRequest::authorize()` is not tidying — `validateResolved()` runs `authorize()` first, so a member who posts a malformed score gets 403 rather than 422. Left in the controller, the Form Request would have validated first and answered a question the caller was not entitled to ask: a 422 describes the shape of a payload, and describing it to someone who may never send one is a small disclosure that costs nothing to avoid.

**A `unique` validation rule and a `unique` database constraint are not two spellings of the same thing.** The rule is a `SELECT` followed later by an `INSERT`, and everything between them is a window. It gives the caller a good error most of the time; the constraint is what actually holds. Both are needed, and they answer different questions — one belongs in the response, the other belongs in the schema.

**A validation rule can be *literally* right and still refuse a correct request.** `required_if:status,closed` inspects the payload. The rule it is implementing is about the row. Those coincide only when the caller closes a week in one request, and the natural two-step — record the evidence, then close — was being rejected 422 for missing fields the row already held.

## AI assistance used

- **Implementation was AI-assisted.** The endpoint list, status codes, the conditional rule and the Day 12/Day 13 boundary were fixed by the day card before the session opened; the AI wrote the Resources, Form Requests and controllers to that specification.
- **Prompt C**, plus the day's concurrency question: *"Which of my endpoints would behave incorrectly if two requests arrived at the same moment?"* Every claim was tested against the running application before it was accepted or dismissed — see the prompt log for which were real.
- **One framework claim was checked against the source rather than accepted.** Scoped bindings resolve the parent relationship by name, and the assumption was that `{week}` would find `weeklyEntries()`. Reading `Model::childRouteBindingRelationshipName()` shows it computes `Str::plural(Str::camel($childType))`, so `{week}` would have looked for a `weeks()` relation that does not exist. The parameter is named `{weekly_entry}`; the URL segment is still `/weeks/{id}`.

## AI output rejected / corrected

1. **The boolean query filter was written with a bare `boolean` rule, and `?active=true` returned 422.** Laravel's `boolean` rule accepts `true, false, 1, 0, "1", "0"` and rejects the strings `"true"` and `"false"` — it was written for form posts, where a browser sends 1 or 0. A query string is not a form post, and `?active=true` is what every HTTP client actually sends. Found by running it, not by reading it. Corrected by normalising in `prepareForValidation()` rather than loosening the rule, so `?active=maybe` is still a 422. The JSON bodies elsewhere need none of this: `{"is_active": false}` carries a real boolean.
2. **The prescribed `required_if` was implemented literally and refused the two-step close.** Corrected by merging the persisted `evidence` and `outcome_score` into the input before validation, so `required_if` is applied to the state the row will actually be in. `rules()` still carries the rule verbatim; a week with neither field recorded is still refused.
3. **The first draft of `SkillController::store()` returned a Resource through an incoherent ternary** that would have produced 200 where the card requires 201. It parsed, so `php -l` said nothing. Rewritten to `->response()->setStatusCode(201)` before it ever ran — which is the argument for reading a generated method rather than only running it.
4. **The duplicate-assessment message used `:input`, which interpolated the wrong field** and produced *"A 8 score of this type is already recorded"*. The placeholder resolves to the value of the attribute the rule is attached to, which is `skill_id`, not `type`. Found by reading the response body rather than the rule.

## Applied to client work

Not yet. Two things transfer directly. The first is the ordering point: putting the permission check in `FormRequest::authorize()` rather than the controller body is a one-line move that fixes a whole class of "422 before 403" disclosure, and it applies to every client project with a Form Request in it. The second is the `boolean` rule on query strings — that is a bug waiting in any filtered index endpoint that has only ever been called from a form.

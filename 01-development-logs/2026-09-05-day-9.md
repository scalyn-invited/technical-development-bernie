# Day 9 — Friday 5 September — Feature and Unit Testing + Week 2 Practical Assessment

**Scheduling note:** Day 9 was originally scheduled Friday 4 September. Displaced by one day within the same week per framework §2 (rescheduled, not skipped) and logged here rather than silently absorbed.

## Built
Full feature test suite for the Order API (`OrderApiTest.php`, 18 tests / 47 assertions) covering CRUD, authentication, role-based authorisation (owner vs approver), validation, structured error responses, JSON response shape, and an N+1 query regression guard. Added a true database-free unit test (`OrderPolicyTest.php`) that exercises the `OrderPolicy` class in isolation using plain PHPUnit, no `RefreshDatabase`, no HTTP layer. Completed the Week 2 practical assessment: one authenticated endpoint, one database relationship, one automated test suite, demonstrated in a single run.

## Learned
A differential query-count test (compare query count at 3 records vs. 10 records and assert equality) proves N+1 doesn't scale with data size, without needing to hardcode a "correct" query number that becomes stale the moment the endpoint legitimately changes. A true unit test isolates a *decision* (does the Policy return true/false) from its *enforcement* (does the controller correctly call `authorize()`) — testing only at the HTTP layer can hide a broken Policy method if the controller happens to compensate for it.

## Got wrong
1. **First draft of the create-order test never attempted to spoof `user_id` in the payload.** It asserted the order ended up owned by the authenticated user, but never proved the controller would *reject* an attacker-supplied `user_id` — a mass-assignment/IDOR class of bug the original test suite couldn't have caught.
2. **`destroy` authorization was tested only from the success side initially.** The non-owner-cannot-view case was covered, but the equivalent non-owner-cannot-delete case was missing — the more consequential gap of the two, since delete isn't reversible.
3. Found a real `array_merge_recursive` collision bug while writing the JSON-structure test for `index` — a pagination `meta` key was colliding with a custom `additional()` call on the Resource Collection. This wasn't found by AI review; it was found by writing the structure assertion and watching it fail.

## AI assistance used
- **Prompt A (concept review):** explained Laravel feature testing (Pest/PHPUnit, `actingAs`, `RefreshDatabase`, `assertJson`) before writing any tests.
- **AI provided illustrative example code** for how to structure feature tests (file creation via `artisan make:test`, sample happy-path/401/403/422/404 patterns on a generic `Post` model) — used as a syntax reference only, not as the actual solution to this exercise's real endpoints. All actual test logic for `OrderApiTest.php` and `OrderPolicyTest.php` was written against the real `Order`/`Customer`/`User` models and the real `OrderController`/`OrderPolicy`, not copied from the AI's generic sample.
- **Prompt C (senior review), run twice** on the growing test suite. First pass identified: missing `user_id` spoofing test, missing non-owner-delete test, missing `assertJsonStructure` test, missing query-count regression test, missing DB-free unit test, and a validation test that bundled four invalid fields into one assertion. Second pass (after the first round of fixes) confirmed the two security-relevant gaps were closed correctly — both with negative database assertions (`assertDatabaseMissing`/`assertDatabaseHas` proving *nothing* changed), not just status-code checks.
- Every AI-identified gap was tested and confirmed real before being treated as fixed — none turned out to be a false positive this session.

## Still cannot explain
Why `OrderPolicyTest.php` covers the *negative* case for `update`/`delete` (non-owner cannot) but doesn't isolate the *positive* approver-override case at the policy-unit level — that path is currently only proven through the slower, heavier feature tests. Left as an open, named gap rather than closed silently.

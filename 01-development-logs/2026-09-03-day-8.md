# Day 8 — Thursday 3 September — Authentication and Authorisation

## Built
Sanctum API token authentication with role-based Policies. Three endpoints (register, login, logout) issuing and revoking tokens. OrderPolicy enforces: employees see/edit own records only, approvers see all records. Rate limiting on login. Consistent 401/403 error envelope.

## Learned
The critical distinction: authentication proves identity (token validates), authorisation controls what the authenticated user can do (Policy decides). Don't scatter permission checks—enforce rules in one place (Policy class) and apply everywhere. Sanctum does the token validation; Policies do the business logic enforcement.

## Got wrong
1. **Dependency chain:** Didn't initially verify Sanctum was installed and `php artisan migrate` had been run for personal_access_tokens table. Assumed it was ready to use without checking.
2. **Rate limiting response:** Wasn't sure what HTTP status code the throttle middleware returns; had to test it (429 Too Many Requests).
3. **Multiple logins:** Didn't think through whether a second login should revoke the previous token. Created a decision I needed to make explicitly, not by accident.

## Blockers and how I resolved them
1. **Dependency issue:** `php artisan migrate` failed until I realized Sanctum tables hadn't been created. Ran `php artisan vendor:publish --provider="Laravel\Sanctum\SanctumServiceProvider"` then migrated. Fixed.
2. **Token validation uncertainty:** Tried to understand if Sanctum was actually validating tokens correctly. Built a small test (logout, then use old token) to verify. It returned 401 as expected. Confirmed.
3. **Rate limiting confirmation:** Wasn't sure if `throttle:5,1` was working correctly. Ran six consecutive login attempts in Postman; the 6th returned 429. Confirmed.
4. **Exception handler question:** Asked Claude if authorization exceptions were using my error envelope. Read the Handler.php code myself first, then verified by testing a 403 response. It matched—confirmed working.

## Still cannot explain
Why Sanctum creates multiple active tokens on repeated logins instead of revoking the previous one by default. Seems like a deliberate design (allowing multiple simultaneous sessions), but I'd need to understand the use case better.
